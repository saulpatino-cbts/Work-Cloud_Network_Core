# Dev deploy workarounds (REVERT before prod)

These are **dev-only expediencies** taken to unblock the `211-deploy-azure-split`
deploy after partial-apply failures left orphaned Azure resources. They are
documented here so they can be reverted/handled deliberately for the prod run.

## 1. AI Foundry account name bumped `-aif` → `-aif2` (dev only)

**File:** `infra/terraform/environments/azure/dev/workload/main.tf`

```hcl
foundry_account_name = "cna-dev-eus2-aif2"   # was "cna-dev-eus2-aif"
foundry_project_name = "cna-dev-eus2-aif2-proj"
```

**Why:** the original `cna-dev-eus2-aif` account was **soft-deleted** by a prior
failed teardown/apply. Cognitive Services / AIServices accounts reserve their
name (subscription + region scoped) while soft-deleted, so recreating with the
same name fails with `409 FlagMustBeSetForRestore ... soft-deleted ... purge it
first`. Bumping the suffix sidesteps the soft-delete graveyard without a manual
purge.

**Revert plan (for prod, and for dev once cleaned up):**
- Prod is **NOT** bumped — it stays `cna-prod-eus2-aif`. Before the prod run,
  confirm no soft-deleted `cna-prod-eus2-aif` exists:
  `az cognitiveservices account list-deleted --query "[?name=='cna-prod-eus2-aif']"`
  If one exists, purge it (no purge protection on Cognitive accounts):
  `az resource delete --ids "/subscriptions/<sub>/providers/Microsoft.CognitiveServices/locations/eastus2/resourceGroups/<rg>/deletedAccounts/cna-prod-eus2-aif"`
- For dev, revert the name back to `cna-dev-eus2-aif` once the soft-deleted ghost
  is purged or its retention lapses (~ default 48h–7d for Cognitive accounts).
- **Durable fix already in place:** `provider "azurerm"` now sets
  `features { cognitive_account { purge_soft_delete_on_destroy = true } }` in
  both dev and prod workload `providers.tf`. This purges the account on a
  Terraform-managed destroy, so future `terraform destroy` runs won't leave a
  reserved name. (It does NOT fire on the RG-level `az group delete` teardown —
  see open follow-up below.)

## 2. Deleted 5 Key Vault secrets from the live vault (dev, manual)

**Vault:** `cna-dev-scus-kv2` (kept — only the secrets were deleted)

Secrets deleted so Terraform recreates them on the next apply:
- `cna-database-url`
- `cna-nextauth-secret`
- `cna-entra-client-secret`
- `cna-credential-encryption-key`
- `cna-applicationinsights-connection-string`

**Why:** a prior apply wrote these to the vault but died before persisting state,
so the next apply hit `already exists - needs to be imported into State`.
Deleting them lets Terraform create them cleanly. Acceptable in dev because the
values are (re)generated/derived by the deploy. **Note:** `nextauth_secret` and
`credential_encryption_key` are REGENERATED by this — fine in dev (nothing
depends on the old values yet), but in prod prefer `terraform import` over delete
to avoid rotating live secrets.

**Revert plan (for prod):** do NOT bulk-delete prod secrets. If prod hits the
same `already exists` collision, `terraform import` each secret into state
instead (adopts existing values, no rotation). Three of the five secrets have
`lifecycle { ignore_changes = [value] }` so import preserves their values; the
other two (`database_url`, `appinsights_connection_string`) re-sync to the
current tfvar value on apply.

## Open follow-up (not yet implemented)

The root cause is that `330-teardown.yml` runs `az group delete --no-wait` and
clears the Terraform state blobs immediately, while Azure is still deleting (and
soft-deleting) resources. To stop this recurring:
- drop `--no-wait` so the RG fully deletes before state is cleared, AND
- purge the soft-deleted **Cognitive account** by name in teardown (the
  `cleanup-stale-ai-resources.ps1` script currently targets the wrong/legacy
  OpenAI name and only soft-deletes — it should purge `cna-<env>-<region>-aif`).
- The **Key Vault** cannot be purged (purge protection is enabled by tenant
  policy); rely on `recover_soft_deleted_key_vaults = true` to recover the
  same-named vault on redeploy, or bump `key_vault_name_suffix` as a last resort.
