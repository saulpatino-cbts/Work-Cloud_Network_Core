Executive Summary

A full source-code audit of the CNA Platform (apps/cna-web — Next.js 15, React 19, TypeScript, Tailwind CSS v4, Auth.js v5, Prisma) was conducted against three industry standards: WCAG 2.1 Level AA, W3C HTML5/CSS specifications, and the OWASP Top 10 (2021) / ASVS v4.0. All 47 findings were identified through direct code analysis — not automated scanning — providing higher fidelity than tool-only approaches.

The platform is well-architected with solid security foundations: Entra ID authentication, server-side session validation on every protected route, parameterised Prisma queries eliminating SQL injection risk, and a layered CSP configuration. However, several gaps require remediation before enterprise client deployment or any accessibility certification claim.

✅ Strengths

  • Entra ID / OIDC authentication with DB-backed sessions
  • Server components validate membership on every protected route
  • Parameterised Prisma ORM — no SQL injection risk
  • CSP header present with frame-ancestors 'none'
  • X-Frame-Options, X-Content-Type-Options, HSTS deployed
  • Server Actions use Auth.js CSRF protection for form submissions
  • External links use rel="noopener noreferrer"
  • Select elements have aria-label attributes
  • lang="en" set on root HTML element

🚨 Critical Gaps

  • unsafe-inline in script-src negates XSS protection
  • Help modal has no focus trap, no Escape key, no dialog role
  • Navigation SVG icons are invisible to screen readers
  • Collapsible findings rows missing aria-expanded
  • No rate limiting on expensive Server Actions
  • SSRF risk on unvalidated customerLogoUrl input
  • Colour contrast fails WCAG AA on secondary text
  • No global focus-visible styles for keyboard nav
⚠️ Recommended Action

The 5 CRITICAL and top 10 HIGH findings should be resolved before presenting the platform to enterprise clients or making any WCAG AA conformance claims. Wave 1 items (7 tasks) can be completed in approximately 2–3 developer days.

🎯 Sprint 5 Recommended Execution Order

  1. [OWA-01] Implement nonce-based CSP — replace unsafe-inline in script-src (next.config.ts L23)
  2. [WAI-03] Rewrite sp-help-modal.tsx using native <dialog> or Radix UI Dialog primitive
  3. [WAI-01/02] Add aria-hidden / aria-label to all sidebar SVG icons and toggle button
  4. [WAI-04/05] Add aria-expanded + aria-controls to findings collapsible rows
  5. [OWA-07] Add domain allowlist validation for customerLogoUrl (SSRF fix)
  6. [WAI-10] Add global :focus-visible styles to globals.css
  7. [WAI-09] Fix colour contrast — adjust text-navy-400 token or dark-mode alias
  8. [WAI-16] Add skip-to-main-content link in dashboard layout
  9. [OWA-02] Add per-user rate limiting to AI generation and discovery Server Actions
  10. [W3C-02] Add aria-hidden="true" focusable="false" to all decorative SVGs

OWASP Top 10 & ASVS v4.0 Findings

17 findings
Wave 1 — Critical

Must fix before first paid client

Critical OWA-01 unsafe-inline Script CSP in Production
OWASP A05:2021 Security Misconfiguration ASVS 14.4.6 next.config.ts L23

The production Content Security Policy contains "script-src 'self' 'unsafe-inline'", completely disabling XSS protection. Any stored or reflected XSS payload executes in full. The code comment acknowledges this is known ("nonce-based script CSP is the recommended next upgrade") — but it remains unimplemented. Next.js 15 has first-class nonce support via middleware.

Remediation

Generate a nonce in Next.js middleware, pass via x-nonce header, and update the CSP to "script-src 'self' 'nonce-{NONCE}'". This also requires wrapping all inline scripts with the nonce prop.

Critical OWA-07 customerLogoUrl Not Validated — Server-Side Request Forgery (SSRF) Risk
OWASP A10:2021 SSRF ASVS 5.2.6 deliverables/actions.ts L93

The customerLogoUrl field is read verbatim from form input and passed to the AI content generator without any URL validation. If the generated HTML causes a server-side fetch (or embeds the URL in a way that triggers fetching), internal Azure metadata endpoints (e.g., http://169.254.169.254/) could be probed. Even without server fetching, an unsanitised URL in AI-generated HTML poses XSS risk.

Remediation

Validate customerLogoUrl against an explicit domain allowlist before use. Reject any URL whose hostname is not in the approved CDN list (cdn.cbts.com, storage.azure.com, etc.).

Wave 2 — High

Required for OWASP rating and production hardening

High OWA-02 No Rate Limiting on Expensive Server Actions
OWASP A07:2021 Auth Failures ASVS 2.2.1 deliverables/actions.ts · discovery/actions.ts

Server Actions for AI generation (generateDeliverable, generateAllAssessments) and discovery (startDiscovery, startAllDiscovery) have no rate limiting. An authenticated user or session replay can trigger hundreds of expensive Azure OpenAI and Azure discovery operations in rapid succession, causing cost overruns and DoS.

Remediation

Implement per-user rate limiting using @upstash/ratelimit or a sliding-window Redis counter. Limit: 5 AI generation requests per 60 seconds per user. 1 discovery job per credential per 5 minutes.

High OWA-03 CSRF Protection Bypassed on Delete Engagement Action
OWASP A01:2021 Broken Access Control ASVS 4.2.2 delete-engagement-button.tsx L28–30

The delete button invokes the Server Action via startTransition() with a manually constructed FormData object — bypassing the Auth.js v5 CSRF cookie check that is tied to <form> element submissions. This allows the action to be triggered from cross-origin pages if the session cookie is present.

Remediation

Wrap the delete action in a proper <form> element with a submit button, or use Auth.js getCsrfToken() to generate and manually verify CSRF tokens for programmatic calls.

High OWA-04 Middleware Cookie Fallback Accepts Non-Secure Tokens in All Environments
OWASP A07:2021 ASVS 3.3.1 middleware.ts L19–21

The middleware accepts both __Secure-authjs.session-token and the non-Secure authjs.session-token cookie in all environments, including production. An invalid or forged non-Secure cookie passes the middleware guard, loading the dashboard layout and leaking engagement names and user email before the server component validates the real session.

Remediation

Guard the non-Secure fallback with process.env.NODE_ENV !== 'production' to ensure production only accepts the __Secure- prefixed cookie.

High OWA-05 Job ID Enumeration via Timing Side Channel
OWASP A01:2021 Broken Access Control ASVS 4.1.2 api/discovery-jobs/[jobId]/route.ts L9–27

The API route returns 401 for unauthenticated requests (fast, no DB hit) and 404 for valid-but-inaccessible job IDs (slower, DB hit). An unauthenticated attacker can probe CUID-space job IDs and use the timing difference to confirm whether a given job ID exists in the database.

Remediation

Ensure the 401 response is returned before any database operations. The current code flow is correct — audit that no future refactor moves the DB lookup above the auth check.

High OWA-06 No Server-Side MIME / Magic-Byte Validation on Document Uploads
OWASP A04:2021 Insecure Design ASVS 12.1.1 documents/ upload action

With a 52 MB body size limit configured for document uploads, there is no visible server-side content-type enforcement or magic-byte validation. Users can upload files with spoofed MIME types (e.g., an executable disguised as a PDF) which will be stored in Azure Blob and potentially served back to the browser.

Remediation

In the document upload Server Action, validate file magic bytes using the file-type npm package. Allowlist: application/pdf, text/plain, image/png, image/jpeg. Reject all others.

WCAG 2.1 Level A & AA Findings

23 findings
ℹ️ Audit Method

All findings were identified through direct JSX/TSX source code analysis. Browser-based automated scanning (axe, WAVE) was not used — findings reflect real structural and semantic issues rather than surface-level heuristics.

Wave 1 — Critical (Level A Failures)

Blocking basic assistive technology use

Critical WAI-01 All Navigation SVG Icons Have No Accessible Name (SC 1.1.1)
WCAG 1.1.1 Non-text Content — Level A engagement-sidebar.tsx L12–88

Every NAV_ITEMS entry contains an inline SVG with no <title>, aria-label, or aria-hidden. When the sidebar is collapsed, the SVG icons are the only content in each navigation link. Screen readers announce raw path data or nothing meaningful.

Remediation

For decorative icons next to visible text: add aria-hidden="true" focusable="false" to the SVG. For icon-only links (collapsed state): add aria-label={item.label} to the <Link> element when collapsed.

Critical WAI-02 Sidebar Toggle Button Has No Accessible Name (SC 4.1.2)
WCAG 4.1.2 Name, Role, Value — Level A engagement-sidebar.tsx L145–163

The sidebar collapse/expand button uses title attribute only. The title attribute is not reliably announced by screen readers (especially on mobile AT and VoiceOver) and does not satisfy SC 4.1.2. The button also lacks aria-expanded to communicate its current state.

Remediation

Replace title with aria-label. Add aria-expanded={!isCollapsed} and aria-controls="engagement-nav". Add a matching id="engagement-nav" to the <nav> element.

Critical WAI-03 Help Modal Fails Multiple WCAG Criteria (SC 4.1.2, 2.1.1, 1.3.1)
WCAG 4.1.2 · 2.1.1 · 1.3.1 — Level A sp-help-modal.tsx L19–242

The SP Help Modal is implemented as a plain <div> with no dialog semantics. Six separate failures:

① No role="dialog" — screen readers don't know it's a dialog. ② No aria-modal="true" — AT can navigate behind the backdrop. ③ No aria-labelledby pointing to the <h2>. ④ Focus is not trapped inside the modal. ⑤ Focus is not restored to the trigger on close. ⑥ Escape key does not close the modal.

Remediation

Replace with native <dialog> element (provides built-in Escape key, focus scoping, and aria-modal) or use @radix-ui/react-dialog which handles all six issues correctly with minimal API surface.

Critical WAI-04 Findings InstanceRow Buttons Missing aria-expanded (SC 4.1.2)
WCAG 4.1.2 Name, Role, Value — Level A findings-client.tsx L83–102

The InstanceRow expand/collapse button renders no aria-expanded attribute. The expand state is conveyed only by SVG rotation (a visual-only transform). Screen readers cannot determine whether the panel is expanded or collapsed.

Remediation

Add aria-expanded={open} and aria-controls={`finding-detail-${finding.id}`} to the button. Add id={`finding-detail-${finding.id}`} to the expanded panel element.

Critical WAI-05 Group Header Buttons Missing aria-controls (SC 4.1.2)
WCAG 4.1.2 Name, Role, Value — Level A findings-client.tsx L428–434

The group header button correctly has aria-expanded={isExpanded}, but lacks aria-controls. The association between button and controlled panel is positional only — screen reader users cannot programmatically navigate to the expanded content.

Remediation

Add id to the expanded content <div> (e.g., id={`group-panel-${groupKey.replace(/:/g,'-')}`}) and add aria-controls to the button referencing that ID.

W3C HTML5 & CSS Standards Findings

12 findings
High W3C-01 Raw <img> Elements in Header — Missing width/height, Causing CLS
W3C HTML5 · Core Web Vitals (CLS) app/(dashboard)/layout.tsx L24–33

Two raw <img> elements (light/dark CBTS logos) are used instead of Next.js <Image>. They lack width and height attributes, causing Cumulative Layout Shift during page load. Both elements are always in the DOM (only one visible via CSS), doubling image requests. An eslint-disable comment suppresses the Next.js lint warning.

Remediation

Replace both <img> tags with Next.js <Image> components specifying explicit width and height, and toggle visibility via CSS. Or use a <picture> element with a (prefers-color-scheme: dark) media source.

High W3C-02 All Decorative Inline SVGs Missing aria-hidden (Pervasive)
W3C SVG 1.1 Accessibility · WAI-ARIA 1.2 All component files — pervasive

Every inline SVG icon across all components (sidebar, findings, connections, deliverables, layout) is decorative — supplementing adjacent text labels — yet none carry aria-hidden="true" focusable="false". Screen readers attempt to parse raw SVG path data (e.g., "M3 12l2-2m0 0l7-7 7 7...") as content.

Remediation

Create a shared <Icon> wrapper component that automatically applies aria-hidden="true" focusable="false". For truly standalone meaningful icons, add a <title> element inside the SVG and role="img" on the SVG element.

High W3C-03 Custom Scrollbar Uses Vendor-Prefix Only — W3C Standard Not Implemented
W3C CSS Scrollbars Level 1 globals.css L206–209

The scrollbar styling uses only ::-webkit-scrollbar pseudo-elements — a non-standard vendor extension. The W3C standard scrollbar-color and scrollbar-width properties (supported in Chrome 121+, Firefox, Safari 18.2+) are absent. Firefox users see the default OS scrollbar.

Remediation

Add standard properties to all scrollable elements: scrollbar-width: thin; scrollbar-color: var(--accent) transparent; Keep the vendor-prefix version as a progressive enhancement for older browsers.

High W3C-04 -webkit-font-smoothing: antialiased Disables ClearType on Windows
W3C CSS Fonts Level 4 — Non-standard property globals.css L84–86

-webkit-font-smoothing: antialiased is not a W3C standard and on Windows effectively disables ClearType subpixel rendering, making text appear thinner and lower contrast. This negatively impacts readability for the majority of Windows enterprise users — exactly the target audience for this platform.

Remediation

Remove both vendor-prefixed font smoothing declarations, or scope them to macOS only using a @media screen and (-webkit-min-device-pixel-ratio: 2) query. Allow the OS to apply its default rendering.
